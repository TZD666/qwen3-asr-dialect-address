# 方言地址识别是怎么一步步想出来的

## 一、先不动手，先问这个模型自己会什么

拿到题目我没有立刻想方案。一个 1.7B 的模型摆在这里，先得知道它的能力边界在哪，否则做出来的东西要么在补它根本不缺的东西，要么在指望它做不到的事。

模型卡上的数字是这样的。

| 测试集 | 词错率 |
|---|---|
| AISHELL-2（普通话朗读） | 2.71 |
| Fleurs-zh | 2.41 |
| WenetSpeech 网络 / 会议 | 4.97 / 5.88 |
| KeSpeech（多方言普通话） | 5.10 |
| WenetSpeech-Chuan 难集 | 21.63 |
| 22 种方言对话集 | 15.94 |

第一行和最后一行差了将近六倍。普通话朗读它做得很好，一百个字错不到三个。方言自由对话它错到十六个点。

这个数字要落到地址上才有意义。一条完整地址二十来个字，按十六个点算，平均每条错三个多字。而地址这个东西的容错是零。二环路南四段三十号写成三十一号，快递就到不了。所以真正要解决的是那三个字落在哪里，能不能捞回来。把整体错误率再压低几个点，对一条送不到的地址没有帮助。

## 二、那张方言清单是按省划的，不是按音系划的

接着看它支持哪二十二种。安徽、东北、福建、甘肃、贵州、河北、河南、湖北、湖南、江西、宁夏、山东、陕西、山西、四川、天津、云南、浙江，加上粤语香港、粤语广东、吴语、闽南语。

前十八个基本是省份名，最后四个才是语言学意义上的方言名。这个清单是按行政区划开的，不是按音系开的，两者对不上。四川、云南、贵州、湖北、河南这些确实是官话，浙江说的是吴语，江西是赣语，湖南是湘语，山西是晋语，福建是闽语，安徽境内江淮官话、吴语、徽语混杂。同一张表里，「四川」和「吴语」这两个标签根本不是一个维度上的东西。

差别有多大，看几个音就知道。四川话说武侯区，音是 wu hou qu，普通话也是 wu hou qu，共用一套音系，区别在声调和少数几组声母韵母。粤语完全不同，广州的粤拼是 gwong zau，番禺是 pun jyu，深圳有 -m 韵尾，还有普通话没有的 -p、-t、-k 入声。

第一个设计判断在这里出现。拿普通话拼音去衡量粤语的误识，等于用一把错误的尺子量长度。所以模型给的方言标签不能直接拿来用，我得自己再做一张表，把二十二个标签映射到真正的音系空间。官话系走普通话拼音，粤语走粤拼，闽南和福建走台罗，吴语、浙江、湘、赣没有成熟的罗马化库，只能先用普通话近似，山西和安徽当过渡区处理。

需要如实标注一句。台罗那条路实测跑通了，粤拼没有。粤拼依赖 pycantonese，这台机器上因为网络问题一直没装上，所以粤语目前走的是「普通话拼音·粤语近似」这条降级路径。降级是设计好的，缺库时自动切换并在接口里报出原因，不会让主链路挂掉。但这意味着后面那条广州录音之所以能对，靠的是降级路径而不是粤拼，粤拼的实际增益还没有数据。

这个念头是从方言清单里直接冒出来的，不是后面推出来的。

## 三、它到底怎么运作

然后翻它的配置和代码。结构很清楚。

```
音频 → 24 层音频编码器（128 维梅尔特征，d_model 1024）
        ↓
      28 层 Qwen3 文本解码器（hidden 2048，词表 15 万，上下文 65536）
        ↓
      "language Chinese<asr_text>正文"
```

关键在后半截。解码器就是一个 Qwen3 语言模型，不是一个专用的音素解码器。这一个事实能解释后面遇到的全部三个现象，先说清楚。

语言模型解码意味着，它在每一步都在做一件事，即在声学证据和语言先验之间取平衡。声学告诉它这三个音节是 wu hou qu，语言先验告诉它中文里「五后区」这种常见字组合比「武侯区」这个低频专名更可能出现。两边一加权，它写出「五后区」。

它没有听错。它听得很准，只是选字的时候用错了先验。

同时我注意到，模板里 system 那一段是自由文本，直接进这个解码器。也就是说先验这一项是可以从外面动的。但开源模型卡里没有任何 context 或者 hotword 的字样，这个能力是我从模板结构推断的，只能实测。

## 四、实测发现它给的不是录音稿，是一份译文

跑了几十条真实录音，输出格式上有三件事情超出预期。

普通话录音，输出简体，语种标签 Chinese。

```
我家在成都市武侯区红牌楼街道二环路南四段三十号。
```

粤语录音，标签变成 Cantonese，输出的是粤文，「在」写成「喺」。

```
我住喺广州市天河区体育西路一百零三号。
```

带闽南腔和台湾腔的录音，标签还是 Chinese，输出却成了繁体。

```
好，你聽好啦！厦门市思明區鼓浪嶼龍頭路八十九號，夠有萬南厝嘅煙火氣。
```

三种正字法。同一个模型，同一次调用，输出的书写系统跟着它判断的语种走。

这说明它在把听到的内容渲染成某种书面语。音素转写不会产生这种差别。这件事很合理，解码器本来就是语言模型，语言模型只会写通顺的书面文字。但对下游是个麻烦，我拿到的文本可能是简体、繁体或者粤文中的任意一种，还夹着「喺」「厝」「嘅」这类只在特定方言里成立的字。

这里有一个后来才发现的便宜可占，先按下不表。

## 五、把问题写成一个式子

到这一步材料够了，可以定性了。

ASR 在求的是这个。

```
argmax P(文字 | 音频)
```

我要的是这个。

```
argmax P(真实地址 A | 音频 x)
```

展开。

```
P(A|x) ∝ P(x|A) · P(A)
           声学似然    地址先验
```

前一项模型做得很好，词错率两到五个点就是证据。问题全在后一项。模型有先验，但它的先验是 P(通用中文文本)，我需要的是 P(真实存在的地址)。这两个分布差得很远。地名是长尾，通用语料里「五后」的频率高过「武侯区」，于是长尾被常见词压掉。

所以要补的不是声学能力，是把先验换掉。而先验这个东西不需要训练，它就是一张表，即哪些地址真实存在。

顺便说一句，这也解释了为什么零训练是对的。如果模型的声学能力不够，那要训练。现在它声学能力很好，缺的是一张表，那就给它一张表。

## 六、错的是字，音还在

这个判断需要证据。真实录音里的两条，是最干净的证据。

一条天津话，模型输出「天津和平区滨江道一百六十八号全叶厂十四楼」。天津没有全叶厂，有劝业场。

```
全叶厂  quan ye chang
劝业场  quan ye chang
汉字全错，拼音距离 0.000
```

一条成都话，模型输出「花牌坊高通巷三十八号」。成都没有高通巷，有交通巷。

```
高通巷  gao tong xiang
交通巷  jiao tong xiang
拼音距离 0.067
```

后面这条错得有规律。西南官话见系不颚化，普通话里 g、k、h 在细音前颚化成了 j、q、x，西南官话大量保留古读，所以街读 gai，鞋读 hai，交读 gao。这不是随机错误，是一条可以写下来的规则。

于是刚才按下的那个便宜也可以兑现了。繁体简体在拼音空间里距离为零。

```
廣州市越秀區 vs 广州市越秀区   距离 0.000
```

第四节里那个正字法的麻烦，在音的空间里自动消失了。同一件事解释了两个现象，说明这个坐标系选对了。

## 七、为什么距离要加权

在拼音空间做匹配，标准编辑距离不够用。它把每个替换都算成代价 1，会把 n 和 l 不分这种系统性音变，判成和随机替换一样远。

方言音变是有结构的，那就把结构写进代价里。

```
cost(a → b) 与 P(a 被听成 b) 反向
```

n 和 l 互换给 0.10，平翘舌给 0.12，前后鼻音给 0.08 到 0.12，见系不颚化给 0.20，浊音清化给 0.35。这张表现在有 20 条声母规则和 26 条韵母规则，每条都标了适用的方言区。

严格说，这些代价应该是混淆概率的负对数，用标注语料估出来。现在是手设的，只保证一件事，即越普遍越规律的音变代价越低。这是一个未校准的近似，不是真的对数似然，后面会说怎么补。

还有一个细节值得说。距离要分两层算，外层在音节序列上做对齐，内层算音节之间的声母代价加韵母代价。如果把整串拼音拼成一个字符串再算编辑距离，chang an 和 cha ngan 会因为音节边界错位产生大量虚假代价。地址里这种情况很多。

## 八、地址库为什么必须分级

有了距离，就要有一张表去匹配。第一个念头是把地址库直接喂给模型的 system 位，让它自己去偏。这条路走不通，原因是规模。

Google 的 CLAS 论文披露过 contextual biasing 的规模特性，候选在数百到数千条时增益最大，上万条时优势明显收窄。全国 POI 上亿条，直接注入必然退化。

但地址有一个非常好的性质，它是严格的树。

```
全国 → 省(34) → 市(337) → 区县(2843) → 区内道路小区(几千)
```

如果把四级当成独立维度做笛卡尔积，假设空间是这么大。

```
34 × 337 × 2843 × 347 = 11,303,557,618
```

一百一十三亿。而实际合法的链条要少得多。每个条目沿着 parent 往上回溯，只能得到唯一一条父链，所以库里有多少个条目就有多少条合法链，一共 3561 条。

```
11,303,557,618 / 3,561 ≈ 317 万倍
```

层级不是一个软性的加分项，它是一个硬约束。它给所有不合法的组合分配零概率，「成都市 + 江北区」这种链根本不会被构造出来。三百多万倍的空间缩减，全部来自这一条结构先验。

缩到几千条之后，候选规模正好落在 CLAS 说的那个甜区。这时候再注入才有意义。

## 九、分级带来的第二个红利

分级还有一个当初没预料到的好处，是真实录音逼出来的。

有一条录音是这样的。

```
哎呀，真的烦，求的要死！你能不能给我寄到那个花牌坊高通巷三十八号碧园公寓？
```

说话的人在抱怨，全程没提四川，没提成都，没提金牛区。他只说了一个街名和一个巷名。

这在真实场景里太常见了。人报地址给熟人时，默认对方知道自己在哪个城市。ASR 再准也补不出没说过的字。

但树能补。花牌坊街这个条目的 parent 指向金牛区，金牛区指向成都市，成都市指向四川省。只要命中最深的那一层，上面三级沿着树一路回溯出来。

```
四川省成都市金牛区花牌坊街交通巷38号碧园公寓
```

这一条输出里，只有花牌坊和交通巷是听到的，省市区三级是推出来的，门牌是规则抽的，碧园公寓是原样保留的。四种来源，一条地址。

回溯出来的父链因此不能算证据，这一点在打分时必须区分开，否则一个只命中了路名的链，会因为自动补上了三级行政区而显得证据充分。

## 十、库不全的时候会发生什么

省市区三级可以离线穷举，一共 3214 条，来自 GB/T 2260 的行政区划代码表，全国全量。这一级是封闭集。

街道、道路、小区不是。全国道路和小区是百万量级，而且一直在变。这一级离线穷举不可能，必须靠高德或者百度的 POI 接口。我先做了一个 347 条的精选路级库把链路跑通，接口留在那里。

这个取舍的代价，在真实录音里立刻现形了。

有一条贵阳话录音，模型听得完全正确。

```
贵阳市云岩区中华中路一百二十号喷水池国贸广场二十三楼
```

贵阳确实有中华中路。但我的库里只有中华北路和中华南路，没有中华中路。

```
中华中路 vs 中华北路   距离 0.250
```

0.250 在阈值以内，于是系统把一个本来正确的转写「纠正」成了中华北路，还给了 confident。

这条要单独拎出来讲，因为它暴露的是这套方法的边界。三道阈值防的是「库里有更像的候选」，防不住「库里根本没有正确答案」。当正确答案不在候选集里，任何排序算法都只能在错的里面挑一个。这是覆盖率问题，排序解决不了。

「街道和小区必须接高德」这句话，就是被这个反例逼出来的。它不是一条功能清单上的待办。

## 十一、怎么给候选打分

候选链有了，要排序。我用一个线性打分函数。

```
score(A) = 0.50·sim + 0.20·cov + 0.15·prior + 0.15·depth − 0.25·conflict
```

四个正项各自对应贝叶斯式子里的一块。

sim 是音相似度，各层命中按层级特异性加权平均，它是 P(x|A) 的代理。层级特异性这么给，省 0.6、市 0.8、区 1.0、街道 1.1、路和 POI 1.2，越具体的层级命中越有说服力。

cov 是覆盖率，即命中片段占输入汉字的比例，它衡量这条候选能解释多少输入。

prior 是链上条目的先验热度，它是 P(A) 里可以查表的那部分，接 POI 热度、人口密度或者历史下单频次。

depth 是证据条数，取 min(命中数, 3) / 3。注意是命中数，不是链的层数，回溯出来的父链不计入。

conflict 是减项。输入里如果有另一个强命中的行政区，而它不在这条链上，就要扣分。这里踩过一个坑，第一版把路级也算冲突，结果「解放碑」和「民权路」这两个同属渝中区的地标互相扣分，把正确答案从第一名打到第三名。它们是互相印证，不是冲突。所以冲突只看行政区层级。

拿上一节那条抱怨的录音走一遍。

| 项 | 值 | 怎么来的 |
|---|---|---|
| sim | 0.967 | 花牌坊 1.000 与 交通巷 0.933 的加权平均 |
| cov | 0.207 | 29 个汉字里命中了 6 个 |
| prior | 0.750 | 链上四级条目按层级权重的加权平均 |
| depth | 0.667 | 2 条证据，min(2,3)/3 |
| conflict | 0 | 没有别的行政区强命中 |

```
0.50×0.967 + 0.20×0.207 + 0.15×0.750 + 0.15×0.667 − 0.25×0 = 0.737
```

这个例子正好解释了权重为什么这么分配。覆盖率只有 0.207，因为这个人说的二十九个字里，有二十三个是在抱怨。如果覆盖率权重给得高，正确答案会因为说话人啰嗦而被罚分。真实语音里绝大部分内容都不是地址，所以覆盖率只配拿 0.20，而音相似度拿 0.50。

诚实地说，这五个权重是我按上面这套道理手设的，不是拟合出来的。它们的和是 1，让 total 读起来像一个 0 到 1 的置信度，但它并不是一个校准过的概率。这是目前方案里数学上最弱的一环。正确的做法是把它当作一个 learning to rank 问题，用标注数据跑 MERT 或者结构化感知机把权重学出来，再用保序回归做概率校准。做这件事的前提是有足够的标注数据，现在还没有。

## 十二、两个音节不算证据

全国表入库之后，冒出来一批离奇的匹配。「中山路」里的中山撞上中山市，「广场」撞上广昌县，「河南话」里的南话撞上南华县。

这不是 bug，是统计上的必然。我算了一下库里的情况。

```
2 音节地名（含别名）共 3026 个
去重后只有 2584 个不同的拼音串
794 个名字落在有碰撞的拼音串上，占 26.2%
```

四分之一的两字地名在读音上撞车。最狠的一个是 xiangcheng，它同时对应相城区、乡城县、襄城县、项城市、襄城区、芗城区，六个行政区分布在江苏、四川、河南、湖北、福建，写法五种，读音一种。gulou 对应七个条目，其中四个是南京、福州、开封、徐州各自的鼓楼区。

换成信息论的说法，在 2843 个区县里定位一个，需要大约 11.5 比特。两个汉字音节实际提供的熵远低于这个数，因为汉语音节分布极不均匀，地名用字又高度集中。所以一次两音节匹配，携带的信息量不足以单独支撑一个结论。

规则就从这里来。两音节及以下的命中标记为弱命中，它不能单独成链，不能作为冲突去扣别人的分，也不能触发落选删除。只有同一条链上有强命中来印证它，它才算数。

还有一条更细的。如果一条链最深的那个命中是靠两字别名撞上的，这条链不成立，父级的强命中不能替它担保。南阳市下面有十二个县，随便哪个县的两字别名撞上文本，「南阳市」这个强命中都会去印证它。「阳河」被匹配成唐河县就是这么来的。

## 十三、什么时候该说不知道

最危险的失败模式不是识别不出来，是自信地答错。上一节那个中华中路就是。

上下文注入的实测把这个风险坐实了。拿一条模型本来听得完全正确的普通话录音，往 system 位里塞不同的候选，看它会不会把「红牌楼」改掉。六个条件跑下来是这样。

| 注入内容 | 输出 |
|---|---|
| 不注入 | 红牌楼 |
| 单条误导候选「红牌坊街道」 | 红牌楼 |
| 误导候选 + 花牌坊街 | 红牌坊 |
| 误导候选 + 春熙路 | 红牌坊 |
| 两条都指向红牌坊 | 红牌楼 |
| 只给花牌坊街 | 红牌楼 |

注入确实会把听对的地名改错，这一点坐实了。但触发条件不是简单的「误导证据越多越容易翻」。单独一条误导候选它顶住了，两条都指向红牌坊时它也顶住了，反而是误导候选配一个指向别处的候选时翻了车，而那个陪跑的候选跟不跟红牌坊押韵都无所谓。

我没有把这个规律解释清楚。能确定的只有两件事，即这条通道真实存在，以及它的效果不单调、不可预测。这恰恰是第二遍解码不能无条件采信的理由。原始记录在 `eval/reports/context_injection.json`。

这就需要拒识。决策论里它有标准形式，即带拒绝选项的贝叶斯决策。损失是高度不对称的。

```
L(送错地址)     ≫  L(让用户点一下确认)
```

一次错误投递的代价，是重新配送加上客诉，可能几十块。一次确认的代价，是用户多点一下。两者差着两三个数量级。在这种损失结构下，最优策略是只在后验概率足够高时才自动决策，否则拒识。这就是 Chow 的拒识规则，阈值由损失比决定。

落成三道确定性的闸门。

第一道看分差。Top-1 和 Top-2 的差小于 0.06，并且两者指向不同的行政区，判 ambiguous，吐 N-best 让人确认。只有指向不同行政区才算真歧义，同一个区里「主路选哪条」的分歧不影响送达，不该拦下来。

第二道看相似度。Top-1 的音相似度低于 0.62，判 reject，保留原文不改。

第三道最硬，门牌、楼栋、单元、室号绝不进这个模块，只走纯规则抽取。库里不可能穷举每一扇门，这部分只能从语音里听出来。

第三道刚刚被自己违反过一次。有一条上海话录音，模型吐出「南京西路八百一百八号」。这不是合法的中文数字，两个百连着出现。旧的解析器是个纯累加器，算成 800 + 100 + 8 等于 908 号，理直气壮写进了门牌字段。我说门牌绝不猜，结果解析器在猜。现在改成带位值校验的解析，位值不递减就判非法，原文原样保留标未核验，门牌字段留空。

## 十四、现在到哪一步了

文本模式二十四句评测集，归一化完全匹配 24/24，行政区三级全对，门牌以下 95.8%，全部 confident。这一档只测后处理链路，用朗读稿当作完美 ASR 输出。

真实录音跑了四十三条有效音频。挑得出来的正面案例是全叶厂纠正成劝业场、高通巷纠正成交通巷、以及那条只说了街名却补全出四川省成都市金牛区的抱怨录音。反面案例有三类。第一类是中华中路被改成中华北路，库不全导致的错误纠正。第二类是「巴适的板」「地道甘肃味儿」这类方言尾巴漏进了地址串，方言词表还不够厚。

第三类最值得说，因为它是第十二节那条弱命中规则的反噬。澳门和台湾其实都在库里，省级条目带着别名。但「澳门」「台湾」都只有两个音节，被判成弱命中，不能单独成链。结果一句澳门地址里，别的两音节碰撞反而赢了，系统给出吉林省白山市，判 partial。一句台湾地址给出上海市闵行区，判 ambiguous。

弱命中规则挡住了「阳河」撞唐河县，同时也压住了真的叫澳门的澳门。这条规则用音节数当代理来估信息量，对短的真地名是误伤。正确的做法是估每个名字自身的区分度，而不是一刀切按长度。

真实录音的成套评测还没跑。二十四句评测集的音频要按编号录齐，才能出裸模型和改造后的对照表。现在这四十三条是随手测的，没有对齐标注，只能当案例，不能当指标。这是当前最大的空白。

## 十五、下一步该补的数学

按价值排。

第一件是把权重学出来。现在五个权重手设，应该用标注数据做 learning to rank，MERT 或者结构化感知机都行，再用保序回归把 total 校准成真实概率。校准之后，第十三节那两个阈值就不用手调了，直接由损失比算出来。

第二件是把 P(x|A) 做真。现在用拼音加权距离当声学似然的代理，隔了一层。接 Qwen3-ForcedAligner 对 Top-K 候选做强制对齐打分，拿到的是真正的声学似然。这一步对吴语、浙江、湘、赣这四个没有成熟罗马化库的方言尤其重要，它们现在只能用普通话近似，信号很弱。这件事仓库里还没有代码，只是方案。

第三件是把音变代价表估出来而不是设出来。有了带标注的方言语音，混淆矩阵可以直接统计，代价取负对数似然，那时候距离才是真的对数概率。

第四件是接高德 POI，配合用户定位。定位半径内的道路优先，这是最便宜也最有效的先验，能直接把第十节那个中华中路的问题解决掉。

第五件是把弱命中规则从「数音节」改成「估区分度」。现在两音节一刀切判弱，误伤了澳门、台湾这类真实存在的短地名。应该给每个名字算一个自身的区分度，比如它在全库里的拼音碰撞数取对数，碰撞多的压低，碰撞少的放行。这样阳河撞唐河县照样被挡，澳门不会被连坐。

第六件是用模型自己的 n-best。现在只取贪心解码的一条输出。开 beam search 拿 n-best 和 token 级的对数概率，候选生成和声学似然都能更贴近模型真实的不确定性，而不是从一条已经坍缩的输出反推。
